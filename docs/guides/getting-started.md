# Getting started with impetus

## Using it

Add `[deps.impetus]` to your `cyrius.cyml` and include `lib/impetus.cyr` (2D) or `lib/impetus-3d.cyr` (3D): the
[README](../../README.md#using-it) has the declaration and two complete programs. Code moving from the Rust crate
1.4.0 should read the [migration guide](migration-2.0.md), which maps each Rust idiom and covers the seven API
changes.

## Building it

```sh
cyrius deps                                # vendor the stdlib, and hisab for the tests
cyrius build src/main.cyr build/impetus    # compile
cyrius test                                # tests/*.tcyr; must be warning-free
cyrius distlib --all                       # dist/impetus.cyr and dist/impetus-3d.cyr
```

`CLAUDE.md` has the full cleanliness check, and `CONTRIBUTING.md` the parity scripts.

## Layout

- `src/` — the library. No `src/` file includes another: `cyrius.cyml`'s `[lib]` (2D) and `[lib.3d]` (3D) list the
  modules in dependency order, and that order is the resolution order. In order:
  - the foundation, shared by both profiles: `error`, the generated `constants*` and `crmath_data`, `crmath`
    (correctly rounded exp, sin, cos, hypot, pow, atan2), `mathx` (Rust's std semantics), `fmtf` (shortest float
    digits), `vec`, `config`, `material`, `units`, `force`, `types`, `arena`, `contact_tracker`, `spring`, and the
    broadphase (`aabb_tree`, `spatial_hash`);
  - each profile's backend: `b2_types`, `b2_narrowphase`, `b2_raycast`, `b2_state`, `b2_joints`, `b2_contacts`,
    `b2_solver`; or `math3` (glam's 3D math) and the `b3_*` files in the same roles;
  - `particle`; the profile's `b2_world` or `b3_world`, then the shared `world`;
  - JSON: the shared `json`, then the profile's `b2_json` or `b3_json` (its `BodyState`);
  - snapshots: the shared `snapshot`, the profile's `b2_snapshot` or `b3_snapshot`, then `world_snapshot`.
- `src/main.cyr` — the build's entry point. Its top level is `var r = main(); sys_exit_group(r);`. Use
  `sys_exit_group`, not `syscall(SYS_EXIT, r)`: the latter is exit(2), which ends only the calling thread, so the
  program hangs once it has spawned a worker.
- `tests/` — the per-module `.tcyr` files, auto-discovered by `cyrius test`. `tests/lib_2d.cyr` and
  `tests/lib_3d.cyr` mirror the two module lists for test compiles. The shared `*_cases.cyr` files hold tests that
  run on both profiles, each included after a profile's list. `tests/golden/` is the oracle's corpus, replayed by
  `parity_2d.tcyr` and `parity_3d.tcyr`. The `.bcyr` files are the benches and the `.fcyr` files the fuzz targets.
- `scripts/` — `oracle/` (the golden generator, which drives `rust-old/`, and `validate.py`, which recomputes the
  corpus), `surface_parity.py`, `rust_test_ledger.py`, `bench_record.py` and `doc_examples.py`.
- `rust-old/` — the Rust 1.4.0 crate, the parity oracle. Never edit it.
- `docs/development/` — the port plan, `state.md`, the roadmap, the parity record and the Rust-test ledger.

## Changing a module

1. Edit `src/<module>.cyr`. A shared module is compiled by both profiles, so test both.
2. Keep its golden rows passing. A generated file (`src/constants*.cyr`, `src/crmath_data.cyr`, `tests/golden/`) is
   regenerated by `scripts/oracle/`, never edited.
3. Behavior that differs from `rust-old/` needs an ADR first ([`../adr/template.md`](../adr/template.md)). New physics
   with no oracle gets reference tests instead of golden rows.
4. Run the cleanliness check in `CLAUDE.md`; `cyrius test` must be warning-free.
5. Re-run the benches and record them against Rust's, then update the CHANGELOG and `state.md`.

A new module goes into `[lib]` (and `[lib.3d]` when shared) at its place in dependency order, and into the matching
`tests/lib_*.cyr`. `scripts/surface_parity.py` fails when a mirror drifts from its list.
